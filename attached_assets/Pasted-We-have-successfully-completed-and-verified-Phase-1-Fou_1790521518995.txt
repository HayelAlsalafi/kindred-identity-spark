2. USER MODEL
============================================================

Create a proper users table/model.

At minimum support:

- id
- email
- password hash or the fields required by the selected authentication system
- display name
- role
- status
- createdAt
- updatedAt
- lastLoginAt

Use appropriate:

- Primary key
- Unique constraint on email
- Indexes where appropriate
- Timestamps

Do not store plaintext passwords.

Do not expose password hashes through API responses.

============================================================
3. AUTHENTICATION
============================================================

Implement a secure authentication mechanism appropriate for the current stack.

Support:

- Registration only if appropriate for the selected product architecture
- Login
- Logout
- Session persistence
- Current authenticated user endpoint

At minimum provide an endpoint equivalent to:

GET /api/auth/me

and appropriate login/logout endpoints.

Use secure session/token practices appropriate for the architecture.

Do not invent a custom insecure authentication mechanism if the existing stack provides a suitable established approach.

Document the authentication choice and why it was selected.

============================================================
4. AUTHORIZATION
============================================================

Implement server-side authorization.

This is critical.

Do NOT rely on frontend route hiding.

For example:

A USER must NOT be able to call Admin APIs simply by manually entering their URL.

Admin authorization must be enforced by the backend.

Create reusable authorization middleware/guards where appropriate.

Example:

requireAuthenticatedUser()
requireAdmin()

Avoid duplicating authorization logic across every endpoint.

============================================================
5. ADMIN ACCESS
============================================================

The existing:

/admin

route is currently only a boundary.

Connect it to the real authentication state.

Behavior:

Unauthenticated user:
→ cannot access admin functionality.

Authenticated USER:
→ cannot access admin functionality.

Authenticated ADMIN:
→ can access admin functionality.

Do not build the complete Admin Dashboard yet.

Only establish the secure foundation.
